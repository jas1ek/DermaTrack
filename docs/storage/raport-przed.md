# D2 - Raport „przed”: stan danych na urządzeniu

## Tabela D2

| Miejsce | Co znaleziono | Ryzyko |
|---|---|---|
| `Library/Preferences/polsl.DermaTrack.plist` | Klucz `dermatrack.lesions.v1`; `LesionService` zapisuje zakodowany JSON z dokumentacją znamion przez `UserDefaults` (kodowanie JSON nie jest szyfrowaniem) | **Wysokie** - lokalny zapis danych o znamionach bez szyfrowania na poziomie aplikacji. |
| `Documents/LesionPhotos/` | 1 plik JPG, katalog o rozmiarze ok. 1,1 MB | **Średnie** - lokalna fotografia zmiany skórnej; nie potwierdzono ochrony istniejącego pliku ani wyłączenia z backupu. |
| `Library/Caches` | 4 pliki: `libraries.list`, `functions.data`, `functions.list`, `libraries.data` | **Niskie (wstępnie)** - stwierdzono obecność plików cache, ale nie wykazano w nich danych wrażliwych; wymaga sprawdzenia zawartości i pochodzenia. |
| `tmp` | 0 plików w momencie badania | **Niskie** - brak plików podczas pomiaru; możliwe przejściowe pliki w innych momentach. |
| Kod logowania | Wystąpienia `print`/podobnych tylko w `Services/LesionService.swift` | **Średnie (potencjalne)** - instrukcje logowania mogą ujawniać dane znamion, lecz nie zweryfikowano ich argumentów; brak potwierdzonego wycieku. |
| Kopie zapasowe | Nie wykryto `isExcludedFromBackup` w skanowanych plikach Swift | **Średnie/wysokie** - ryzyko dołączenia odtwarzalnych danych medycznych i zdjęć do kopii zapasowej; rzeczywisty zakres backupu nie został sprawdzony. |
| 
| iOS Keychain / sesja Supabase (część backendowa) | W osobnej wersji DermaTrack użyto Supabase Swift 2.55.3 z domyślnym `KeychainLocalStorage` do przechowywania sesji (JWT i refresh token). Potwierdzono przywrócenie sesji po ponownym uruchomieniu aplikacji. | **Niskie/średnie** - zastosowano Keychain, lecz nie zweryfikowano klasy dostępności wpisów ani zachowania po połączeniu obu części aplikacji. |
| Logi aplikacji / Supabase Auth (część backendowa) | Zaimplementowano rejestrację, logowanie i wylogowanie przez Supabase Auth; wykonywano testy funkcjonalne uwierzytelniania. Nie udokumentowano wyniku przeglądu logów SDK i konsoli pod kątem tokenów lub haseł. | **Średnie (potencjalne)** - ewentualny zapis tokenów w logach mógłby ujawnić sesję; w dotychczasowych materiałach nie wykazano takiego zdarzenia. |
| Pamięć aplikacji / Storage (część backendowa) | Z prywatnego bucketu `lesion-photos` pobrano i wyświetlono testowy JPG. W aplikacji obraz był obsługiwany jako `Data` i `UIImage`; nie ustalono, czy SDK utworzył kopie w `Library/Caches`, `tmp` lub `Documents`. | **Średnie (potencjalne)** - przetwarzanie zdjęć w pamięci jest konieczne, ale niezweryfikowane kopie na dysku mogłyby utrwalać dane medyczne. |
| Wylogowanie / sesja (część backendowa) | Metoda `auth.logout()` przenosi użytkownika do ekranu logowania; przetestowano logowanie pacjenta i dermatologa po wylogowaniu. Nie wykonano osobnego badania pozostałości wpisów Keychain i buforów obrazów. | **Średnie (potencjalne)** - nie potwierdzono pełnego usunięcia lokalnych pozostałości sesji i zdjęć po wylogowaniu; nie wykazano też ich pozostawania. |
| `UserDefaults` / ustawienia interfejsu | W części iOS zastosowano `@AppStorage("bodySilhouetteStyle")` do zapamiętywania wyboru typu sylwetki. | **Niskie** - zapis ustawienia interfejsu nie wymaga przechowywania informacji medycznych; należy unikać powiązania go z dokumentacją pacjenta. |
| `UserDefaults` / ustawienie blokady biometrycznej | W części iOS zastosowano `@AppStorage("biometricLockEnabled")` do zapamiętywania preferencji włączenia blokady biometrycznej. | **Średnie** - lokalną flagę preferencji można zmienić; nie może ona samodzielnie potwierdzać uwierzytelnienia ani zastępować sprawdzenia sesji. |
| Pamięć procesu / `PhotosPicker` | Podczas importu fotografii do aplikacji trafiają tymczasowe dane obrazu, m.in. `PhotosPickerItem`, `Data` i `UIImage`. Nie potwierdzono trwałego zapisu tych roboczych danych. | **Średnie** - przetwarzane są wrażliwe fotografie; należy ograniczać czas ich utrzymywania w pamięci i sprawdzić, czy nie powstają zbędne kopie. |
| `Library/Preferences` / ustawienia UIKit | W pliku preferencji zidentyfikowano klucz systemowy `com.apple.UIKit.UISplitViewController.Root`. | **Niskie** - nie wykazano, aby wpis zawierał dane medyczne; ustawienie jest zarządzane przez UIKit. |
| CoreLocation / MapKit | Nie potwierdzono trwałego zapisu dokładnej lokalizacji GPS.  | **Niskie obecnie / średnie po wdrożeniu** - obecnie brak stwierdzonego zapisu; dokładna lokalizacja będzie wymagała minimalizacji i obsługi odmowy zgody. |
| `AuthViewModel` / pamięć procesu | W części Backend/Security identyfikator UUID zalogowanego użytkownika i rola `patient` / `dermatologist` znajdują się w stanie aplikacji. Uprawnienia do danych są dodatkowo kontrolowane przez RLS. | **Niskie/średnie** - sam stan UI nie daje dostępu do backendu, ale nie powinien być traktowany jako źródło autoryzacji. |
| `AddLesionTestView` / pamięć procesu | W testowym formularzu pola nazwy, lokalizacji na ciele i opisu znamienia przechowywane są w `@State` podczas edycji. | **Średnie** - są to wrażliwe informacje o znamieniu obecne w pamięci aplikacji; nie stwierdzono odrębnego trwałego zapisu w tym ekranie. |
| `LesionPhotoRecord` / pamięć procesu | Po pobraniu historii fotografii aplikacja przechowuje w tablicy `[LesionPhotoRecord]` identyfikatory zdjęć, daty i ścieżki plików w Storage. | **Średnie** - metadane mogą ujawniać historię obserwacji zmian skórnych; dostęp do ich pobrania ograniczają polityki RLS. |
| `LesionSharingService` / pamięć procesu | Podczas udostępniania znamienia i cofania dostępu aplikacja wykorzystuje `lesionID`, `dermatologistID` oraz tekstowy status operacji. Stan uprawnienia zapisuje backend w `lesion_shares`. | **Niskie/średnie** - identyfikatory i status mogą ujawniać informację o relacji pacjent-lekarz; lokalny komunikat nie stanowi dowodu nadania dostępu. |
| `AuthRootView` / pamięć procesu | W implementacji lokalnego odblokowywania użyto zmiennych `isUnlocked`, `isAuthenticating` i `biometricError`. Nie potwierdzono jeszcze poprawnego blokowania widoku po każdym powrocie z tła. | **Średnie** - nieprawidłowy reset stanu mógłby pozostawić ekran z danymi dostępnym bez ponownego potwierdzenia tożsamości. |
